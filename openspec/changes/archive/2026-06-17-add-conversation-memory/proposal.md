# 变更提案：增加对话记忆管理

## 背景

当前 interview-agent 的 `/api/chat` 接口依赖前端每次传入 `history` 数组。用户刷新浏览器或重新打开页面后，对话历史完全丢失，无法延续上一次面试模拟。

对于面试准备场景，用户希望：
- 刷新页面后仍能继续上一轮对话。
- 同一人多次访问能被识别为同一用户。
- 历史记录存储在服务端数据库，而不是本地存储。

## 目标

实现服务端持久化的对话记忆管理，支持刷新后自动恢复最近会话。

## 范围

###  included（范围内）

1. 用户身份识别机制（基于浏览器 stable ID）。
2. 服务端数据库存储（SQLite）。
3. 会话（conversation）和消息（message）两张核心表。
4. 新增/改造 RESTful API：
   - `GET /api/conversations`
   - `GET /api/conversations/:id/messages`
   - `POST /api/conversations`
   - `DELETE /api/conversations/:id`
   - 改造 `POST /api/chat` 支持按会话自动保存。
5. 前端加载时自动恢复最近会话。
6. 轻量服务器部署方案（SQLite 文件路径、备份策略、PM2 配置）。

### excluded（范围外）

1. 用户登录/注册系统。
2. 跨设备同步（同一账号多设备共享历史）。
3. 会话标题 AI 自动生成（MVP 阶段取首条消息前 20 字）。
4. 消息搜索、导出、分享。

## 验收标准

- [ ] 刷新浏览器后，最近 10 条消息自动显示在聊天窗口。
- [ ] 同一 `user_id` 可以创建多个独立会话，互不干扰。
- [ ] `/api/chat` 发送消息后，用户和 AI 消息均写入数据库。
- [ ] 删除会话后，关联消息级联删除。
- [ ] 部署到轻量服务器后，数据库文件持久化不丢失。

## 风险与假设

- **风险**：用户清缓存或换浏览器会丢失身份。可通过后续「自定义标识」功能缓解。
- **假设**：当前为单实例部署，SQLite 足够支撑未来 1-2 年的数据量。
