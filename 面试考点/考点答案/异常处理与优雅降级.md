# 异常处理与优雅降级

> **面试高频题**："如果工具调用失败了怎么办？LLM API 超时了怎么办？你的系统怎么保证不崩？"

---

## 一、为什么异常处理是面试重点

面试官问异常处理，考察的是**系统健壮性思维**。

- 只讲" Happy Path "（正常流程）的候选人 = 没上线过真实项目
- 能讲清楚"出错时怎么办"的候选人 = 有工程经验

**面试考点文件中的要求**：
- 考点1："增加异常捕获与重试"、"错误参数纠正、优雅降级"
- 考点3："3轮未解决转人工"、"超时30s降级为模板回复"

## 二、项目中的四层异常防护

```
┌─────────────────────────────────────────────────────────────┐
│                    异常防护体系                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   第一层：调用层防护                                          │
│   ├── LLM API 超时 → 降级为模板回复                            │
│   ├── LLM API 报错 → 重试 1 次，再失败返回兜底文案              │
│   └── 网络断开 → 前端提示"连接中断，请重试"                    │
│                                                             │
│   第二层：工具层防护                                          │
│   ├── MCP Server 无响应 → 跳过 MCP，只用 RAG 结果              │
│   ├── RAG 检索失败 → 跳过 RAG，LLM 基于通用知识回答             │
│   └── 知识库文件缺失 → 返回空结果，不打断主流程                 │
│                                                             │
│   第三层：数据层防护                                          │
│   ├── 参数校验失败 → 返回错误信息，不执行危险操作               │
│   ├── 返回值格式异常 → 用默认值兜底                            │
│   └── 空值/undefined → 给默认值或空字符串                      │
│                                                             │
│   第四层：用户体验层防护                                       │
│   ├── 加载超时 → 显示"正在思考中..."动画                       │
│   ├── 生成中断 → 保留已生成内容，提示"生成中断"                 │
│   └── 连续失败 → 建议用户"换个问法试试"                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 三、每层详细实现

### 第一层：调用层防护

#### 1. LLM API 超时处理

```typescript
// 设置 30 秒超时
const TIMEOUT_MS = 30000;

async function callLLMWithTimeout(messages: Message[]): Promise<string> {
  return new Promise((resolve, reject) => {
    const timeout = setTimeout(() => {
      reject(new Error('LLM_TIMEOUT'));
    }, TIMEOUT_MS);

    streamChat(messages)
      .then((result) => {
        clearTimeout(timeout);
        resolve(result);
      })
      .catch((err) => {
        clearTimeout(timeout);
        reject(err);
      });
  });
}
```

**超时后的降级策略**：
```typescript
try {
  const answer = await callLLMWithTimeout(messages);
  return answer;
} catch (error) {
  if (error.message === 'LLM_TIMEOUT') {
    // 降级：返回模板回复
    return generateTemplateReply(userQuestion);
  }
  throw error;
}
```

#### 2. LLM API 报错重试

```typescript
async function callLLMWithRetry(
  messages: Message[],
  maxRetries = 1
): Promise<string> {
  let lastError: Error;

  for (let i = 0; i <= maxRetries; i++) {
    try {
      return await callLLMWithTimeout(messages);
    } catch (error) {
      lastError = error as Error;
      
      // 只有特定错误才重试
      if (isRetryableError(error)) {
        // 指数退避：第1次等 1s，第2次等 2s
        await delay(1000 * (i + 1));
        continue;
      }
      
      // 不可重试的错误直接抛出
      throw error;
    }
  }

  // 重试用完，返回兜底
  return '抱歉，服务暂时不可用，请稍后再试。';
}

function isRetryableError(error: unknown): boolean {
  // 以下错误可以重试
  if (error instanceof Error) {
    return (
      error.message.includes('timeout') ||
      error.message.includes('ECONNRESET') ||
      error.message.includes('429') ||  // 限流
      error.message.includes('503')     // 服务不可用
    );
  }
  return false;
}
```

**面试要点**：
- 只重试"可能恢复"的错误（网络超时、限流），不重试"必然失败"的错误（参数错误、认证失败）
- 重试间隔用指数退避，避免雪崩
- 重试次数不超过 2 次，避免无限等待

### 第二层：工具层防护

#### 1. MCP 调用失败降级

```typescript
async function getMCPResult(query: string): Promise<string | null> {
  try {
    const result = await runMCPForQuery(query);
    return result;
  } catch (error) {
    console.error('[MCP Error]', error);
    // MCP 失败不影响主流程，返回 null，后续只用 RAG
    return null;
  }
}

// 使用
const mcpResult = await getMCPResult(message);

const systemContent = buildSystemPrompt({
  ragChunks: chunks,
  mcpResult: mcpResult,  // 可能为 null，buildSystemPrompt 内部处理
  history: memory,
});
```

#### 2. RAG 检索失败降级

```typescript
async function getRAGChunks(query: string): Promise<Chunk[]> {
  try {
    return await retrieveRelevantChunks(query, 3);
  } catch (error) {
    console.error('[RAG Error]', error);
    // RAG 失败，返回空数组
    // LLM 会基于通用知识回答，System Prompt 里有"不知道就承认"的约束
    return [];
  }
}
```

**关键点**：每个外部依赖都有 try-catch，失败时返回安全默认值，不打断主流程。

### 第三层：数据层防护

#### 1. 参数校验

```typescript
interface ChatRequest {
  message: string;
  user_id: string;
}

function validateChatRequest(body: unknown): ChatRequest {
  if (!body || typeof body !== 'object') {
    throw new Error('请求体必须是对象');
  }

  const { message, user_id } = body as Record<string, unknown>;

  if (!message || typeof message !== 'string' || message.trim().length === 0) {
    throw new Error('message 不能为空');
  }

  if (message.length > 2000) {
    throw new Error('message 不能超过 2000 字');
  }

  if (!user_id || typeof user_id !== 'string') {
    throw new Error('user_id 不能为空');
  }

  return { message: message.trim(), user_id };
}
```

#### 2. 返回值安全处理

```typescript
// ❌ 危险：直接访问可能不存在的属性
const score = chunk.embedding[0];

// ✅ 安全：默认值兜底
const score = chunk?.embedding?.[0] ?? 0;

// ❌ 危险：假设数组一定有元素
const firstChunk = chunks[0].content;

// ✅ 安全：先判断再访问
const firstChunk = chunks.length > 0 ? chunks[0].content : '';
```

## 四、异常处理设计原则

### 1. 快速失败（Fail Fast）

参数校验在第一层就做，不要让错误数据流到后面。

```typescript
// ✅ 好的做法：入口处就校验
app.post('/chat', async (req, res) => {
  try {
    const { message, user_id } = validateChatRequest(req.body);
    // ...
  } catch (error) {
    res.status(400).json({ error: error.message });
  }
});
```

### 2. 优雅降级（Graceful Degradation）

每个外部依赖失败，都要有降级方案。

```
正常流程：RAG + MCP + LLM
RAG 失败：0 + MCP + LLM（基于通用知识）
MCP 失败：RAG + 0 + LLM（基于检索结果）
LLM 失败：返回模板回复 / 提示重试
```

### 3. 用户无感知

后端出错了，前端用户应该看到友好的提示，而不是堆栈跟踪。

```typescript
// ❌ 不要这样
res.status(500).json({ error: error.stack });

// ✅ 应该这样
res.status(500).json({ 
  error: '服务暂时不可用，请稍后再试',
  retryable: true 
});
```

## 五、面试话术（完整版）

> **"如果工具调用失败了怎么办？"**
>
> 我们的异常处理分四层防护。
>
> **第一层是调用层**：LLM API 设置了 30 秒超时，超时后降级为模板回复。API 报错时会重试 1 次（只有网络超时、限流等可恢复错误才重试，参数错误不重试），重试间隔用指数退避。如果重试也失败，返回兜底文案"服务暂时不可用"。
>
> **第二层是工具层**：MCP 和 RAG 都有独立的 try-catch。MCP 调用失败返回 null，主流程继续走，只用 RAG 的结果。RAG 检索失败返回空数组，LLM 基于通用知识回答，同时 System Prompt 里有"不知道就承认"的约束防止幻觉。
>
> **第三层是数据层**：请求参数入口处就做校验，防止脏数据流进去。所有可能为空的值都有默认值兜底，不用裸属性访问。
>
> **第四层是用户体验层**：超过 3 秒没响应显示"正在深度思考"，用户可以随时点击停止，连续失败 3 次会提示"换个问法试试"。
>
> 核心原则是：每个外部依赖都可能失败，失败时要有降级方案，用户看到的是友好提示而不是错误堆栈。
