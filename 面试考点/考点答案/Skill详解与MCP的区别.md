# Skill 详解与 MCP 的区别

> **面试高频题**："你做过 Skill 吗？Skill 和 MCP 有什么区别？"、"Harness 里的 Skills 起什么作用？"
> **考点关联**：考点2 第一梯队（AI Agent 核心开发能力）、Harness 研发范式

---

## 一、Skill 是什么

Skill = AI 编码助手的**可复用领域能力包**。

**一句话**：把某个重复性研发流程封装成一个"超级能力"，AI 编码助手（Claude Code、Cursor、阿里内部工具等）加载后就能按固定流程执行。

### 为什么需要 Skill？

没有 Skill 时，每次做同样的事都要重新 prompt：
```
你："帮我在这个项目里插入埋点代码"
AI："请问埋点需求文档在哪？插哪些埋点？"
你："文档在 xxx，要插页面曝光和点击事件"
AI："好的，让我看看代码结构..."
（下次又要重复一遍）
```

有了 Skill 后：
```
你："/埋点"（加载多端埋点 Skill）
AI："已加载多端埋点 Skill。请提供埋点需求文档路径。"
你："doc/track.md"
AI："已解析文档，发现 5 个埋点。开始定位插入位置..."
（下次直接复用，不需要重复说明流程）
```

### Skill 的核心特征

| 特征 | 说明 |
|---|---|
| **流程固化** | 把"解析文档 → 定位位置 → 生成代码 → 插入"流程写成模板 |
| **输入输出明确** | 用 opspec / OpenSpec 定义清楚需要什么、产出什么 |
| **领域专属** | 每个 Skill 解决一个特定领域问题 |
| **团队复用** | 写好一次，团队内所有人都能用 |

## 二、我做过的 Skill 案例

### 1. 多端埋点 Skill

**解决的问题**：埋点需求集中在项目末期，开发同学反复阅读埋点文档、逐一手动插入，效率低、容易遗漏。

**Skill 流程**：
```
1. 读取埋点需求文档（输入）
2. 解析文档，提取埋点列表（事件名、触发时机、参数）
3. 扫描项目代码，定位埋点插入位置（页面曝光 → 页面组件，点击 → 点击回调）
4. 按平台规范生成埋点代码（Rax / React / 小程序语法不同）
5. 插入代码并输出变更摘要（输出）
```

**效果**：团队内下载 **30+**，成为常用工具。

**面试话术**：
> "我独立开发了一个多端埋点 Skill，解决团队里埋点代码重复、标准不统一的问题。先用 opspec 描述清楚输入输出和边界条件，让 AI 生成基础实现，再自己 review 和补全平台差异逻辑。覆盖 Rax / React / 小程序三端，团队内 30+ 下载。"

### 2. 稳定性升级 Skill

**解决的问题**：监控上报体系升级时，人工配置容易出错。

**Skill 流程**：
```
1. 读取升级配置模板
2. 扫描现有监控埋点
3. 对比差异，生成升级脚本
4. 自动更新告警配置
5. 输出变更报告
```

**价值**：固化治理经验，降低同类升级的接入门槛。

### 3. harness-creator Skill

**解决的问题**：跨仓库的 Harness 规范审计和生成。

**Skill 流程**：
```
1. 扫描目标仓库结构
2. 对比 Harness 规范检查清单
3. 生成缺失文件（CLAUDE.md、AGENTS.md、settings.json 等）
4. 输出审计报告
```

## 三、Skill 的目录结构

在 Claude Code / 阿里内部工具中，Skill 通常放在：

```
.claude/
├── skills/
│   ├── multi-platform-track/      # 多端埋点 Skill
│   │   ├── skill.md               # Skill 定义（输入输出、流程）
│   │   └── examples/              # 示例
│   ├── stability-upgrade/         # 稳定性升级 Skill
│   │   └── skill.md
│   └── harness-creator/           # Harness 生成 Skill
│       └── skill.md
├── commands/                      # Slash 命令
├── rules/                         # 规则约束
└── settings.local.json            # 权限配置
```

### skill.md 长什么样

```markdown
# 多端埋点 Skill

## 输入
- 埋点需求文档路径（Markdown 格式）
- 目标平台（rax / react / miniapp）

## 输出
- 埋点代码变更（diff）
- 变更摘要（埋点数量、位置列表）

## 流程
1. 读取并解析埋点需求文档
2. 提取埋点事件列表
3. 扫描 src/ 目录，定位页面和组件
4. 按目标平台语法生成埋点代码
5. 插入代码，输出 diff

## 边界条件
- 不修改 node_modules/
- 已有埋点不重复插入
- 无法定位时标记为"需人工确认"
```

## 四、Skill 和 MCP 的区别

这是面试最核心的问题，必须讲清楚。

### 一句话区别

> **Skill 是"做什么"（领域工作流），MCP 是"怎么连"（通信协议）。**

### 详细对比

| 对比项 | Skill | MCP |
|---|---|---|
| **定位** | AI 编码工具的**扩展能力包** | 跨模型/应用的**标准化通信协议** |
| **解决什么问题** | "如何让 AI 按固定流程完成某类任务" | "如何让模型统一调用外部工具" |
| **封装内容** | 领域工作流（埋点流程、告警查询、MR 创建） | 工具接口（文件系统、数据库、浏览器、API） |
| **作用域** | 特定 AI 工具内部 | 任何支持 MCP 的 Client |
| **复用范围** | 同工具内复用 | 跨工具、跨模型复用 |
| **典型例子** | 多端埋点 Skill、飞猪告警查询 Skill | ChromaDB MCP、浏览器 MCP、文件系统 MCP |
| **关系** | **Skill 可以调用 MCP** | MCP 是 Skill 的底层通信方式之一 |

### 类比理解

```
餐厅比喻：

Skill = 菜谱（宫保鸡丁的做法）
  - 告诉厨师：需要什么食材、什么步骤、什么火候
  - 是"做事的方法"

MCP = 厨房接口标准（统一的食材柜门把手尺寸）
  - 告诉所有厨师：食材柜怎么开、调料怎么取
  - 是"连接的标准"

关系：
  - 菜谱（Skill）里写了"取鸡肉 200g"，厨师通过统一的柜门把手（MCP）打开食材柜
  - 没有 MCP，每个厨师开柜子的方式不一样；没有 Skill，厨师不知道做什么菜
```

### 技术比喻

```
Skill = 业务组件库（Button、Table、Form）
  - 封装了特定业务逻辑
  - 在特定框架内使用

MCP = HTTP 协议
  - 规定了通信格式
  - 跨框架、跨语言通用

关系：
  - 组件库（Skill）内部发请求时，用 HTTP（MCP）和后端通信
  - 你可以用 Skill 而不关心 MCP，也可以用 MCP 直接调工具而不封装 Skill
```

## 五、Skill 和 MCP 在项目中的协作关系

```
┌─────────────────────────────────────────────────────────────┐
│                    AI 编码助手（Claude Code / Cursor）         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌─────────────┐         ┌─────────────────────────────┐   │
│   │   Skills    │         │        MCP Client           │   │
│   │             │         │                             │   │
│   │ • 多端埋点   │◄───────►│  通过 MCP 协议调用外部工具   │   │
│   │ • 稳定性升级 │         │                             │   │
│   │ • harness   │         │ • 向量数据库（ChromaDB）     │   │
│   │   审计      │         │ • 浏览器自动化               │   │
│   │             │         │ • 文件系统                  │   │
│   └─────────────┘         │ • 内部 API                 │   │
│                           └─────────────┬───────────────┘   │
│                                         │                   │
│                                         ▼                   │
│                              ┌─────────────────────┐        │
│                              │     MCP Server      │        │
│                              │  （标准化工具接口）   │        │
│                              └─────────────────────┘        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**协作关系**：
- Skill 定义"做什么任务"
- 任务执行过程中，如果需要查数据库、读文件、调 API，通过 MCP 协议调用外部工具
- **Skill 是上层业务逻辑，MCP 是底层通信协议**

## 六、常见追问

### Q: Skill 和 Function Calling 有什么区别？

**回答**：
> "Function Calling 是模型原生的能力——LLM 输出 JSON 告诉调用方要调哪个函数。Skill 是更高层的概念，是一整套工作流的封装。
>
> 关系上：Skill 内部可能会用到 Function Calling。比如多端埋点 Skill 在执行过程中，可能通过 Function Calling 让 LLM 判断'这个埋点应该插在哪个组件里'。但 Skill 本身定义的是完整的流程（从读文档到插代码），Function Calling 只是流程中的一个技术点。"

### Q: 你们的 Skill 是怎么分发的？团队怎么共享？

**回答**：
> "Skill 放在代码仓库的 `.claude/skills/` 目录下，随仓库一起管理。团队成员克隆仓库后就能用。我们还做了版本管理——Skill 的变更走 MR 流程，有 code review，确保质量。
>
> 对于跨仓库复用的 Skill，我们会抽成独立仓库，通过软链接或包管理的方式引入。"

### Q: Skill 和 Prompt 模板有什么区别？

**回答**：
> "Prompt 模板是一段静态文本，告诉 AI'你该怎么回答'。Skill 是一个完整的执行单元，包含：
> 1. 输入输出定义（opspec）
> 2. 执行流程（分步骤）
> 3. 边界条件（什么时候停止、什么时候报错）
> 4. 可能还包含示例代码和测试用例
>
> 可以把 Skill 理解为'Prompt + 执行逻辑 + 约束条件'的集合，比单纯的 Prompt 模板更结构化、更可复用。"

### Q: 写 Skill 有什么最佳实践？

**回答**：
> "几个关键点：
> 1. **输入输出要明确** — 用 opspec 写清楚需要什么、产出什么，不要模糊
> 2. **流程要可拆分** — 每个步骤独立可测试，方便调试
> 3. **边界条件要完整** — 异常情况怎么处理（文件不存在、解析失败、插入位置找不到）
> 4. **示例要充分** — 给 AI 看正确示例和错误示例，减少幻觉
> 5. **版本管理** — Skill 也是代码，走 MR + Review 流程"

>
