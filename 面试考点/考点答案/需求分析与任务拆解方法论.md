# 需求分析与任务拆解方法论

> **面试高频题**："如果让你从 0 到 1 设计一个 Agent，你会怎么做？"
> **考点3 强调**："不要上来就谈技术，先讲需求分析。"

---

## 一、面试官的四条红线

**考点3 明确指出**：

1. **真正考察什么**：有没有从 0 到 1 设计 Agent 的完整方法论，而不是只会调 API。
2. **雷区一**：上来就聊模型选择 / API 接口 / 框架选型，没有需求分析，**直接扣分**。
3. **雷区二**：只讲怎么搭，不讲怎么验证效果，说明没有真正上线过。
4. **加分项**：讲过程中自然带出真实项目案例。

---

## 二、四步设计流程

```
需求分析 → 任务拆解 → Prompt 设计 → 评测上线
```

### Step 1: 需求分析（最关键，面试先讲这个）

**三个问题必须回答清楚**：

| 问题 | 含义 | 面试助手案例 |
|---|---|---|
| **任务是什么** | Agent 要完成什么核心任务 | 辅助面试回答，让回答更准确、更流畅 |
| **用户是谁** | 使用者是谁，成功标准是什么 | 求职者在面试中被提问，希望获得高质量回答提示 |
| **边界在哪** | AI 做 vs 人做的边界 | AI 提供素材和组织语言，人负责最终表达和临场发挥 |

**面试话术**：
> "如果让我从 0 到 1 设计这个面试助手，我首先做需求分析。任务是辅助面试回答，用户是正在面试的求职者，成功标准是回答准确、有数据支撑、不 hallucination。边界也很清楚：AI 负责检索知识和组织语言，但不代替人说话——最终表达还是求职者自己。"

---

### Step 2: 任务拆解

把核心任务拆成子任务链，每个子任务**独立可测试**。

```
用户提问
    │
    ▼
┌─────────────────┐
│ 1. 意图识别      │  "这是技术题还是行为题？"
│    (Router)     │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. 知识检索      │  "去知识库找相关素材"
│    (RAG/MCP)    │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 3. 上下文组装    │  "把检索结果 + 历史对话组装成 Prompt"
│    (Prompt Eng) │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 4. 答案生成      │  "LLM 基于 Prompt 流式生成"
│    (LLM)        │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 5. 输出格式化    │  "Markdown 解析 + 打字机效果"
│    (Frontend)   │
└─────────────────┘
```

**每个子任务的设计要点**：

| 子任务 | 输入 | 输出 | 可测试标准 |
|---|---|---|---|
| 意图识别 | 用户问题 | 标签：tech/behavior/open | 100 条标注数据的准确率 |
| 知识检索 | 问题 + 意图 | 相关 chunks | Top3 召回率 |
| 上下文组装 | chunks + 历史 | messages 数组 | 人工检查 Prompt 质量 |
| 答案生成 | messages | 流式文本 | BLEU/人工评分 |
| 输出格式化 | 文本流 | UI 渲染 | 前端测试 |

**面试话术**：
> "任务拆解后，我把整个流程分成 5 个独立步骤：意图识别、知识检索、上下文组装、答案生成、输出格式化。每个步骤都有明确的输入输出和可测试标准。比如意图识别，我可以用 100 条标注数据测试准确率；知识检索可以用 Top3 召回率衡量。"

---

### Step 3: Prompt 设计

Prompt 设计不是"写一段提示词"，而是**系统工程**。

#### 三层 Prompt 结构

```
System Prompt（全局约束）
├── 角色定义："你是马倩倩的面试回答助手"
├── 行为约束："基于提供的文档回答，不知道就承认"
├── 格式约束："简洁，1-2 句话一个要点，加粗关键词"
└── 安全约束："不要编造不存在的信息"

Context（动态上下文）
├── 历史对话摘要（长期记忆）
├── 检索到的知识库 chunks（RAG 结果）
├── MCP 工具返回的结构化数据
└── 近期对话历史（短期记忆）

User Prompt（当前问题）
└── 用户的当前提问
```

#### Prompt 设计原则

| 原则 | 说明 | 示例 |
|---|---|---|
| **具体而非抽象** | 不要说"回答得好一点" | "每个要点不超过 2 句话" |
| **加示例（Few-shot）** | 给 LLM 看标准答案 | "参考格式：\\n- **关键词**：描述 + 数据" |
| **加负例** | 告诉 LLM 不要做什么 | "不要大段文字，不要编造数据" |
| **结构化输出** | 让 LLM 按格式输出 | "用 Markdown 列表，每条以 - 开头" |

**面试话术**：
> "Prompt 设计我分三层：System Prompt 负责全局约束（角色、行为、格式、安全），Context 是动态注入的检索结果和对话历史，User Prompt 是当前问题。System Prompt 里我会给具体约束而非抽象要求，比如不说'回答简洁'，而是说'每个要点不超过 2 句话'。还会加 Few-shot 示例，让 LLM 知道标准格式。"

---

### Step 4: 评测上线

没有评测的 Agent 等于没有质量保障的产品。

#### 评测三层指标

```
┌─────────────────────────────────────────────────────────┐
│ 第一层：工具调用准确率                                     │
│ ├── 意图识别准确率（是否分对了题型）                         │
│ └── 知识检索召回率（Top3 是否覆盖了关键信息）                │
├─────────────────────────────────────────────────────────┤
│ 第二层：步骤完成率                                         │
│ └── 从意图识别到答案生成的完整链路成功率                     │
├─────────────────────────────────────────────────────────┤
│ 第三层：端到端结果                                         │
│ ├── 回答准确率（与标准答案对比）                            │
│ └── 用户满意度（点赞/点踩比例）                            │
└─────────────────────────────────────────────────────────┘
```

#### 评测集设计

```
200 条评测集：
├── 常见问题 100 条（技术题 50 + 行为题 30 + 开放题 20）
├── 边界 case 50 条（超长问题、空问题、无关问题）
└── 对抗 case 50 条（诱导 hallucination、问不存在的信息）
```

**面试话术**：
> "评测我分三层：工具层看意图识别准确率和检索召回率，流程层看完整链路成功率，结果层看回答准确率和用户满意度。评测集我设计了 200 条：100 条常见问题 + 50 条边界 case + 50 条对抗 case。上线标准是端到端准确率 > 90%。"

## 三、真实案例：面试助手的设计过程

### 需求分析

```
任务：辅助面试回答
用户：前端/全栈求职者
成功标准：
  1. 回答准确（基于真实经历，不编造）
  2. 有数据支撑（秒开率、问题数等）
  3. 表达流畅（第一人称、简洁、结构化）
边界：AI 提供素材，人负责表达
```

### 任务拆解

```
1. 意图识别 → 正则规则（技术栈/项目/性能/稳定性/开放）
2. 知识检索 → RAG（语义搜索）+ MCP（结构化查询）
3. 上下文组装 → 按模板拼接 System Prompt
4. 答案生成 → qwen-plus 流式生成
5. 输出格式化 → SSE + Markdown 解析 + 打字机效果
```

### Prompt 设计

```markdown
你是马倩倩的面试回答助手...

【行为约束】
- 基于提供的项目文档上下文，以第一人称回答
- 若上下文中没有相关信息，坦诚告知
- 不要编造不存在的信息

【格式约束】
- 简洁，1-2 句话一个要点
- 用 **加粗** 标关键词
- 要点列表，不要大段文字
- 突出个人贡献 + 数据

【安全约束】
- 不要泄露敏感信息
- 不要评价其他公司或同事
```

### 评测标准

```
上线标准：
- 意图识别准确率 > 95%
- RAG Top3 召回率 > 80%
- 端到端回答准确率 > 90%
- 首字延迟 < 2s
```

## 四、常见追问

### Q: 需求分析要分析多久？

**回答**：
> "看项目规模。面试助手这种小项目，需求分析 1-2 天就够了，主要是明确任务、用户、边界。如果是企业级项目，可能需要 1-2 周，还要做竞品分析、用户访谈。关键是不要跳过这一步，直接写代码。"

### Q: 如果需求变了怎么办？

**回答**：
> "Agent 项目需求变更是常态。我们的应对：
> 1. **模块化设计** — 每个子任务独立，改意图识别不影响知识检索
> 2. **Prompt 版本管理** — 每次修改 Prompt 都留版本，方便回滚
> 3. **评测集覆盖** — 改完跑一遍评测集，确保没回退
> 4. **A/B 测试** — 新旧版本并行跑，对比准确率"

### Q: 怎么判断 Agent 准备好了可以上线？

**回答**：
> "三个标准：
> 1. **评测集通过** — 200 条测试 case，端到端准确率 > 90%
> 2. **边界 case 覆盖** — 空问题、超长问题、无关问题都有兜底
> 3. **人工抽检** — 随机抽 20 条回答，人工判断是否符合预期
>
> 都通过了才上线，上线后还要收集真实用户反馈持续优化。"

## 五、面试话术（完整版）

> **"如果让你从 0 到 1 设计一个 Agent，你会怎么做？"**
>
> 我分四步走：需求分析 → 任务拆解 → Prompt 设计 → 评测上线。
>
> **第一步需求分析**，回答三个问题：任务是什么、用户是谁、边界在哪。比如面试助手，任务是辅助回答，用户是求职者，边界是 AI 提供素材、人负责表达。
>
> **第二步任务拆解**，把核心任务拆成独立子任务：意图识别、知识检索、上下文组装、答案生成、输出格式化。每个子任务有明确的输入输出和可测试标准。
>
> **第三步 Prompt 设计**，分三层：System Prompt 做全局约束（角色、行为、格式、安全），Context 动态注入检索结果和对话历史，User Prompt 是当前问题。Prompt 里给具体约束而非抽象要求，还会加 Few-shot 示例。
>
> **第四步评测上线**，分三层指标：工具调用准确率、步骤完成率、端到端结果。评测集覆盖常见 case、边界 case、对抗 case，上线标准是准确率 > 90%。
>
> 面试官最看重的不是用了什么框架，而是有没有从需求到上线的完整闭环思维。
