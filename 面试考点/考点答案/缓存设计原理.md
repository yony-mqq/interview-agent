# 缓存设计原理

> **面试高频追问**："你的缓存是怎么匹配的？是完全相同命中，还是语义相近也命中？"

---

## 一、缓存不是一层，而是两层

我们的项目里有两套完全独立的缓存机制，定位不同：

| 缓存层 | 位置 | 匹配方式 | 存储介质 | 作用 |
|---|---|---|---|---|
| **结果缓存** | `cacheService.ts` | **精确匹配** | SQLite | 相同问题直接返回回答 |
| **Embedding 缓存** | `embedder.ts` | **精确匹配** | 内存 Map | 相同文本不再请求 Embedding API |

**关键区别**：
- 结果缓存：缓存的是 LLM 的**最终回答**
- Embedding 缓存：缓存的是文本的**向量表示**

---

## 二、结果缓存：精确匹配（MD5）

### 代码实现

```typescript
// cacheService.ts
function md5(text: string): string {
  return crypto.createHash('md5').update(text, 'utf-8').digest('hex');
}

const hash = md5(query.trim().toLowerCase());

// 查询
const stmt = db.prepare(
  'SELECT response FROM response_cache WHERE query_hash = ?'
);
const row = stmt.get(hash);
```

### 匹配规则

只有满足以下**全部条件**才算命中：

1. `trim()` — 去除首尾空格
2. `toLowerCase()` — 忽略大小写
3. `md5()` — 字符串完全一致

**示例：**

| 用户输入 A | 用户输入 B | 是否命中同一个缓存 |
|---|---|---|
| "介绍你的项目经验" | "介绍你的项目经验" | ✅ 命中 |
| "介绍你的项目经验" | "介绍一下你的项目经验" | ❌ 不命中（多了"一下"） |
| "你的技术栈" | "你的技术栈是什么" | ❌ 不命中（多了"是什么"） |
| "Hi" | "hi" | ✅ 命中（忽略大小写） |

### 为什么不做语义模糊匹配？

也就是说，为什么 "介绍项目" 和 "介绍一下项目" 不命中同一个缓存？

**原因：**

1. **精确匹配实现简单、零误判**
   - 语义模糊匹配需要额外维护一个 embedding 索引，还要设定相似度阈值
   - 阈值设高了（如 0.9），"介绍项目"和"介绍技术栈"可能误命中，返回错误回答
   - 阈值设低了（如 0.7），命中率又上不去，得不偿失

2. **面试场景下高频问题足够固定**
   - "介绍项目经验" "技术栈是什么" "做过最有挑战的事"
   - 这些问题措辞高度一致，精确匹配已经能覆盖 80% 的命中场景

3. **语义缓存有"污染"风险**
   - "为什么用 React" 和 "为什么用 Vue" 语义上非常接近
   - 如果模糊命中，可能返回一个关于 Vue 的回答给一个问 React 的面试官

> 面试话术："结果缓存我们用精确匹配。原因是面试场景下高频问题措辞固定，精确匹配已经能覆盖大部分场景。语义模糊匹配虽然能提升一点命中率，但引入了误判风险——比如'为什么用 React'和'为什么用 Vue'语义相近但答案完全不同。权衡后选择精确匹配，简单可靠。"

### 缓存准入规则

不是每个问题都缓存，只有满足以下条件才缓存：

```typescript
function isCacheable(query: string): boolean {
  const q = query.trim();
  if (q.length > 100) return false;          // 太长不缓存（可能是追问）
  if (/为什么|怎么|如何|详细|具体|深入/.test(q)) return false;  // 追问词不缓存
  return true;
}
```

**不缓存的原因：**
- 长问题通常包含上下文信息，重复概率低
- 追问类问题需要结合前面 N 轮对话，单独缓存没有意义

## 三、Embedding 缓存：精确匹配（MD5）

### 代码实现

```typescript
// embedder.ts
const embeddingCache = new Map<string, number[]>();
const CACHE_MAX_SIZE = 500;

function md5(text: string): string {
  return crypto.createHash('md5').update(text, 'utf-8').digest('hex');
}

export async function getEmbedding(text: string): Promise<number[]> {
  const cacheKey = md5(text.trim());

  if (embeddingCache.has(cacheKey)) {
    return embeddingCache.get(cacheKey)!;
  }

  // 没命中 → 请求 API
  const response = await client.embeddings.create({ ... });
  const embedding = response.data[0].embedding;

  // 写入缓存
  if (embeddingCache.size >= CACHE_MAX_SIZE) {
    embeddingCache.clear();  // 超上限清空
  }
  embeddingCache.set(cacheKey, embedding);

  return embedding;
}
```

### 匹配规则

和结果缓存一样，也是**整段文本的 MD5 精确匹配**。

```
用户输入 "项目经验" → md5("项目经验") → 查缓存 → 命中/未命中
用户输入 "项目经验 " → md5("项目经验 ") → 查缓存 → 不命中（多了空格）
```

### 为什么不按语义近似匹配 Embedding？

Embedding 缓存的目的是**避免重复调用 Embedding API**，不是做语义检索。

语义检索发生在 `retriever.ts`：

```typescript
// retriever.ts — 这才是语义检索的地方
const scored = store.chunks.map((chunk) => ({
  chunk,
  score: cosineSimilarity(queryEmbedding, chunk.embedding),  // ← 语义匹配
}));
```

**Embedding 缓存层和语义检索层的分工：**

```
用户输入 "项目经验"
    │
    ▼
[Embedder 层] getEmbedding("项目经验")
    │   ├─ md5("项目经验") → 查内存缓存 → 命中？返回向量
    │   └─ 未命中 → 调用 API → 返回向量 → 写入缓存
    │
    ▼ 返回 queryEmbedding
[Retriever 层] cosineSimilarity(queryEmbedding, chunk.embeddings)
    │   ← 这里才是语义匹配，和缓存无关
    ▼
返回 Top3 chunks
```

**关键理解：**
- Embedding 缓存：**相同文本** → 直接复用向量，省一次 API 调用
- 语义检索：**不同文本** → 但向量相近 → 匹配到相关 chunk

如果 Embedding 缓存也做语义近似，那会变成：
```
"项目经验" 的 embedding ≈ "做过什么项目" 的 embedding
→ 缓存语义命中，返回 "项目经验" 的向量
→ 但这两个问题的回答可能不同
```
这会导致**检索结果和实际 query 不匹配**，所以 Embedding 缓存只做精确匹配。

### 为什么不拆分按块缓存？

比如用户输入 "介绍一下你的项目经验和性能优化"，为什么不拆成 "项目经验" 和 "性能优化" 分别缓存 Embedding？

**原因：**

1. **Embedding 模型输入是整句，不是词袋**
   - "项目经验和性能优化" 的向量 ≠ "项目经验" 向量 + "性能优化" 向量
   - 整句的语义是一个整体，拆分会丢失上下文关系

2. **拆分后无法确定切分粒度**
   - "项目经验和性能优化" 拆成两个？那 "接送列表架构和性能优化和稳定性建设" 拆三个？
   - 粒度不固定，缓存 key 的管理会变成噩梦

3. **成本已经够低了**
   - Embedding API（text-embedding-v3）几乎是免费的
   - 缓存的目的只是避免**同一句话在一秒内重复请求**
   - 精确匹配已经足够满足这个场景

> 面试话术："Embedding 缓存也是精确匹配。原因是 Embedding 模型的输入是整句，不是词袋——'项目经验和性能优化' 的向量不等于 '项目经验' 向量加 '性能优化' 向量。语义检索是在 retriever 层通过余弦相似度做的，和 embedder 层的缓存是两套独立机制。"

## 四、两层缓存的分工总结

```
用户输入 "介绍项目经验"
    │
    ├──► [结果缓存] md5("介绍项目经验") → SQLite 查缓存
    │       ├─ 命中？直接返回回答，不走 LLM ✅
    │       └─ 未命中？继续往下走
    │
    ├──► [Embedding 缓存] md5("介绍项目经验") → 内存 Map 查缓存
    │       ├─ 命中？复用向量，不走 API ✅
    │       └─ 未命中？调用 text-embedding-v3，写入缓存
    │
    ├──► [RAG 检索] cosineSimilarity(queryEmbedding, chunk.embeddings)
    │       → 返回 Top3 chunks
    │
    ├──► [Memory 组装] 滑动窗口 + 摘要
    │
    └──► [LLM 生成] streamChat(messages, selectedModel)
                → 写入结果缓存（供下次命中）
```

| 层级 | 匹配方式 | 命中后省了什么 |
|---|---|---|
| 结果缓存 | 精确 MD5 | 跳过 RAG + Memory + LLM 全流程 |
| Embedding 缓存 | 精确 MD5 | 跳过一次 Embedding API 调用 |
| RAG 检索 | 余弦相似度（语义） | —（这是检索本身，不是缓存） |

## 五、面试话术（整段）

> **"缓存是怎么匹配的？语义相近的问题能命中吗？"**
>
> 我们有两层缓存，都是精确匹配。
>
> 第一层是结果缓存，用 SQLite 存储。query 做 trim + toLowerCase 后算 MD5，完全一致才算命中。比如"介绍项目经验"和"介绍一下项目经验"就不会命中同一个缓存。我们没做语义模糊匹配，原因是面试场景下高频问题措辞固定，精确匹配已经能覆盖大部分场景。而且语义模糊有风险——"为什么用 React"和"为什么用 Vue"语义相近但答案完全不同，误判的代价太大。
>
> 第二层是 Embedding 缓存，用内存 Map。也是整段文本的 MD5 精确匹配。这里不做语义近似的原因是：Embedding 缓存的目的是避免同一句话重复调用 API，不是做语义检索。语义检索是在 retriever 层通过余弦相似度做的，和 embedder 的缓存是两套独立机制。另外 Embedding 模型输入是整句，不是词袋，拆分会丢失上下文关系，所以也没有按块缓存。
>
> 两层缓存叠加下来，高频问题第二次请求可以跳过 LLM 全流程，Embedding 层也可以避免重复 API 调用。
